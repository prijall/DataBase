# Runtime memory audit — September 21, 2026

**Scope:** offline inspection of archived logs and pinned public source. No M4 connection, model load, generation, runtime change, binary replacement, or experiment retry was performed for this audit. Public source copies were saved only in the controller's ignored `runs/runtime-memory-source/` directory.

## Finding

The installed backend has a supported environment control, **`LLAMA_ARG_CACHE_RAM=0`**, that disables its separate prompt-state RAM cache. A positive integer sets its MiB limit. The pinned Ollama launcher inherits its own environment when starting that backend and does not pass a competing cache-size argument. Therefore, setting this variable **in the owned temporary Ollama service's environment before startup** is a source-supported way to test disabling that cache without installing software, changing weights, or saving research files on the M4. This propagation is established from source; it has **not been tested live here**. It is a llama.cpp backend control inherited through this pinned Ollama version, not an Ollama HTTP request option or a promise about other versions. [Backend option](https://github.com/ggml-org/llama.cpp/blob/0f3a71be15af836d277c9f918adfafb45732677e/common/arg.cpp#L1712-L1719), [Ollama launch and environment](https://github.com/ollama/ollama/blob/d8ab4b4f0ca24b51d3a46b3bf4f462e58ce66b1f/llm/llama_server.go#L339-L477).

This finding does not rescue the stopped calibration. Its erroneous-solution class has one success in four attempts, so even six further successes could yield only 7/10, below the fixed 8/10 gate. The actual runtime stop was memory pressure; the cohort remains incomplete. Do not rerun, replace, or rescore those cases as a cache experiment.

## What the saved run establishes

The [small-context archive](results/2026-09-21-processbench-small-context/README.md) records a verified 2,048-token context and a separate 224 MiB Metal KV buffer. Its [cache observations](results/2026-09-21-processbench-small-context/runtime-cache-observations.json) show a configured prompt-cache limit of 8,192 MiB and growth from zero to five stored prompts, totaling **408.015 MiB**. The full controller log is bound by SHA-256 `a3adad624e70069947c127dcf2b9b9d167434508d37bd2b2ce30d9a761fe7e75`.

After the sixth response, kernel pressure reached level 2 while reported free memory was 22%; swap usage and swapouts had not increased against baseline. Cleanup subsequently confirmed pressure level 1, 42% free memory, closed research ports, and no owned processes. These observations establish cache growth and a resource stop in the same session. They do not isolate cache growth as the cause, establish a leak, or measure the model's incremental resident memory apart from office activity. The 8,192 MiB cache limit is a ceiling, **not evidence that 8 GiB was allocated**.

## How the limit arises

1. The pinned llama.cpp default sets `cache_ram_mib` to 8192 and enables idle-slot caching. It is independent of the 2,048-token active context. The argument parser reads environment settings before command-line arguments and maps `LLAMA_ARG_CACHE_RAM` to that value. [Defaults](https://github.com/ggml-org/llama.cpp/blob/0f3a71be15af836d277c9f918adfafb45732677e/common/common.h#L627-L632), [environment parsing](https://github.com/ggml-org/llama.cpp/blob/0f3a71be15af836d277c9f918adfafb45732677e/common/arg.cpp#L781-L808).
2. Ollama constructs the backend command with model, context, parallelism and other settings, but no `--cache-ram` override. `SetupLlamaServerCommandEnv` starts from the service's environment and applies library/device updates. The normal inherited default therefore explains the observed limit, absent an external override; the log alone does not prove which environment variables were present. [Pinned launcher](https://github.com/ollama/ollama/blob/d8ab4b4f0ca24b51d3a46b3bf4f462e58ce66b1f/llm/llama_server.go#L339-L477).
3. With a nonzero cache limit, the backend creates a `server_prompt_cache`. Zero skips its creation and disables the dependent idle-slot-saving feature. The cache stores token-associated serialized state in memory; this is not a disk prompt-history feature. [Initialization](https://github.com/ggml-org/llama.cpp/blob/0f3a71be15af836d277c9f918adfafb45732677e/tools/server/server-context.cpp#L1351-L1362), [idle-slot dependency](https://github.com/ggml-org/llama.cpp/blob/0f3a71be15af836d277c9f918adfafb45732677e/tools/server/server-context.cpp#L1420-L1427).
4. For a positive limit, the cache skips an entry larger than its allowance and evicts older entries before allocating a new entry. This bounds the cache's accounted state, not process RSS, model memory, allocator overhead, or total macOS pressure. Zero is the clearest first diagnostic because it removes this cache component rather than introducing an arbitrary tuned size. [Allocation and eviction](https://github.com/ggml-org/llama.cpp/blob/0f3a71be15af836d277c9f918adfafb45732677e/tools/server/server-task.cpp#L1711-L1790).

## Controls that must not be conflated

| Control | Source-supported effect | Limit for this investigation |
| --- | --- | --- |
| `LLAMA_ARG_CACHE_RAM=0` | Disables the separate prompt-state RAM cache at backend startup | Does not remove the active KV buffer or all current-slot prefix reuse |
| Positive `LLAMA_ARG_CACHE_RAM` | Bounds accounted prompt-cache state in MiB | Is not a global memory cap; no positive value selected here |
| `LLAMA_ARG_CACHE_IDLE_SLOTS=0` | Disables one idle-slot-saving behavior | Does not disable every prompt-cache save/load path |
| `LLAMA_ARG_CACHE_PROMPT=0` | Changes the backend default for prompt reuse | Ollama explicitly sends `cache_prompt: true`; this alone is not a reliable way to disable reuse through this client |
| `OLLAMA_KV_CACHE_TYPE` | Selects active KV representation/quantization | Separate numerical change; excluded from the proposed diagnostic |

The pinned server exposes the first three backend cache controls in its [reference documentation](https://github.com/ggml-org/llama.cpp/blob/0f3a71be15af836d277c9f918adfafb45732677e/tools/server/README.md). Ollama explicitly enables reuse in both [completion requests](https://github.com/ollama/ollama/blob/d8ab4b4f0ca24b51d3a46b3bf4f462e58ce66b1f/llm/llama_server.go#L1562-L1567) and [chat requests](https://github.com/ollama/ollama/blob/d8ab4b4f0ca24b51d3a46b3bf4f462e58ce66b1f/llm/llama_server.go#L2162-L2167); its [KV environment setting](https://github.com/ollama/ollama/blob/d8ab4b4f0ca24b51d3a46b3bf4f462e58ce66b1f/envconfig/config.go#L221-L222) is different. No dedicated Ollama API option for the separate RAM-cache limit was identified in this path.

Disabling saved prompt states should cause more recomputation and change latency/memory behavior; it does not change weights, supplied text, or gold labels. It must nevertheless be treated as a new runtime configuration. Backend documentation warns that prompt reuse can change numerical results because different batch shapes need not produce bit-identical logits. Fixed seed and temperature zero therefore do not justify promising identical outputs between cache settings. Active-slot reuse can remain enabled even when the separate RAM cache is absent. [Numerical caveat](https://github.com/ggml-org/llama.cpp/blob/0f3a71be15af836d277c9f918adfafb45732677e/tools/server/README.md#L589), [conditional save/load path](https://github.com/ggml-org/llama.cpp/blob/0f3a71be15af836d277c9f918adfafb45732677e/tools/server/server-context.cpp#L1626-L1643).

## Minimal separate diagnostic proposal — not implemented or run

First obtain a separate decision to implement a **runtime diagnostic**, with no ProcessBench IDs or scientific accuracy gate. Do not reuse the failed calibration report, budget, or evaluation reservation.

- Preserve the existing service wrapper and frozen artifacts. Review a separate diagnostic launcher/profile that places the single cache variable in the **remote service environment** through stdin-only code. Merely exporting it on the controller does not guarantee SSH forwarding. No shell-profile edits, launch-agent changes, environment persistence, binary wrappers/swaps, or installations are needed.
- Keep model identity, active context 2,048, KV type, device, threads, isolation and original resource stops fixed. Bind the diagnostic code and explicit environment value, establish a fresh pre-load baseline, and keep all logs/artifacts on the controller. Use a new service with no resident model; never modify an office server.
- Stage one is one non-generating debug load of a newly authored neutral prompt. Record only the allowlisted cache environment key/value in the owned service event; never dump a full environment. Verify the backend log explicitly reports disabled prompt-state caching, exact target context and idle state, then check memory. The explicit service value and backend initialization message together establish intended configuration and observed uptake. If the control is absent, ambiguous or ineffective, stop; do not add flags experimentally. This stage can test uptake and loading headroom, not cache growth during generation.
- Only under a separately frozen allowance, stage two could issue **at most four** distinct neutral synthetic prompts, each capped at **one generated token**, once each. Use no benchmark material and no response-quality objective. Record raw output, cached-token timings, cache logs and resources around each request; stop on any existing guard. Cap the whole diagnostic at ten minutes including loading and cleanup. Verify owned-process termination. Those four calls would be new runtime-diagnostic completions and must be counted separately.
- A successful single-arm check would show that the setting is applied and the bounded workload remained within the guards. It would not show that the cache caused the earlier pressure, guarantee a twenty-call run, or validate reasoning. A causal memory comparison would require a separately approved matched default/cache-disabled experiment under controlled background load; the archived default run is not such a control.

Human review of the [six existing outputs](results/2026-09-21-processbench-small-context/OUTPUT_REVIEW.md) remains necessary independently of runtime work. A cache fix cannot turn the already unattainable calibration gate into a pass. Any future model-quality study needs a distinct design decision, not continuation of this stopped screen.
